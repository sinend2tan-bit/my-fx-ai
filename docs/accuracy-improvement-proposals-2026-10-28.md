## 課題1：アプリ画面とクラウドスキャンで、判定の物差しが違う

### 根拠（現在のコードで確認）
- モデルの版が別々に進んでいる：app.py は `MODEL_VERSION = 6`、scanner.py は `MODEL_VERSION = 19`。
- 特徴量はどちらも16個だが構成が違う。
  - アプリ側だけにあるもの：`Dev_EMA20_200`、`Vol_Ratio`
  - スキャン側だけにあるもの：`Dev_EMA20`
- 同じ名前で中身が違う指標がある：`Vol_Ratio`
  - アプリ側：ATR ÷ ATRの50本平均（ボラティリティの比）。**学習の特徴量として使用**。
  - スキャン側：出来高 ÷ 出来高の20本平均。**診断専用で、学習には使っていない**（コード内のコメントと診断ログで明示）。
- 学習ラベルの作り方が違う（どちらも「8本先までに上下どちらのバリアに先に触れるか」だが、基準が異なる）。
  - アプリ側：基準価格はシグナル足の**終値**。バリア幅は `max(ATR×1.0, スプレッド×2) + スプレッド`。
  - スキャン側：基準価格は**次足の始値**（実際に取引できる価格に合わせた方式）。バリア幅はちょうど **±1 ATR**。

### 影響
- 画面の判断とスキャンの判断が食い違っても、それだけでは不具合と言えない状態になっている。
- いま蓄積中のフォワード検証で測っているのは、スキャン側の定義による成績だけ。画面側の判断の良し悪しは測れていない。
- 両方を見て取引判断をするとき、混乱の元になる。

### 提案（無料範囲内）
- **案1（すぐ可能・低リスク）**：違いを明記する。画面に「アプリ内分析とクラウドスキャンは別のモデル・別の物差し」という注記を出し、この文書を正とする。変更は表示のみで、判定には触れない。
- **案2（本命・要判断）**：スキャン側の定義に統一する。アプリ側のラベルを次足始値基準・±1 ATR にし、特徴量をスキャン側の16個に一致させる。ただしアプリ側の既存指標（学習ラベル一致率など）の意味が変わるため、実施はフォワード検証の蓄積状況を見てから段階的に。
- **案3**：現状維持。フォワード検証の結果が貯まるまで触らない。
- 推奨：まず案1。統一（案2）は、フォワード検証でスキャン側の物差しの妥当性が見えてから判断する。

### 確認方法
- 案2を実施する場合は、同一データで両者の特徴量とラベルが一致するかを比べるテストを先に作り、一致を確認してから切り替える。

## 課題2：データ本数のしきい値が 221 と 220 で食い違う

### 根拠（現在のコードで確認）
- scanner.py の `bars()` 内に2か所ある。
  - 1301行目：加工前の足が **221本未満**なら打ち切り。
  - 1352行目：末尾足の除外（または4時間足への集約）の後に **220本未満**なら打ち切り。
- 1時間足の経路では「221本 → 未確定の末尾1本を除外 → 220本以上」と実質つながっているが、4時間足の経路では、集約後の4時間足そのものに220本（営業日換算で約55日分）を要求する形になっている。取得期間は90日分なので、休日が重なると静かに分析不能（結果なし）になり得る。同じ数字が経路ごとに違う意味を持っているのが問題の本質。

### 影響
- 通常運用（1時間足・180日分）では問題は出ていない。
- 4時間足の分析が、データ不足で黙って欠けるリスクがある。

### 提案（無料範囲内）
- しきい値を名前付きの定数にまとめ、経路ごとに必要な本数を明示する（例：学習用は220本、事前チェックは「末尾除外を見込んだ本数」として式で書く。4時間足の必要本数は別途定義する）。
- 境界値のテスト（219／220／221本）を追加して挙動を固定する。
- 判断ポイント：4時間足にも220本を必須とするか、それとも本数を下げるか。

### 確認方法
- 境界値テストで各経路の挙動を確認し、4時間足経路の実データ本数をログで確認する。

## 課題3：簡易スキャンの依存が重く、履歴が引き継がれない

### 根拠（現在のコードで確認）
- fx_scan_simple.yml はアプリ用の requirements.txt（streamlit、plotly などを含む9パッケージ、版指定なし）をインストールしているが、fx_scanner_simple.py が実際に使うのは numpy／pandas／yfinance のみ。
- 状態を引き継ぐ仕組み（キャッシュ等）がワークフローに無く、scan_state_simple.json と scan_history_simple.json は実行のたびに消える。
- なお、この簡易スキャンは手動実行専用（workflow_dispatch）のため、影響は限定的。

### 影響
- 毎回のインストール時間の無駄と、簡易スキャンの履歴が蓄積しないこと。

### 提案（無料範囲内）
- 軽量の依存ファイル（numpy／pandas／yfinance、版固定）を新規に作り、ワークフローからそちらを参照する。依存ファイルの追加自体は通常のPRで可能。
- 状態の引き継ぎは、本スキャンと同じキャッシュ方式と成果物バックアップを追加する。
- 注意：ワークフローファイル自体の変更は、権限の都合で GitHub のウェブ画面からの編集が必要（差し替え文面と手順は別途提示できる）。

### 確認方法
- 手動実行で、実行時間が短くなることと、2回目の実行で履歴が引き継がれることを確認する。

## 判断ポイントのまとめ

1. 課題1：案1（違いの明記）だけ先に進めるか／統一（案2）の検討時期をどうするか。
2. 課題2：4時間足の必要本数をどうするか（220本のままか、下げるか）。
3. 課題3：軽量化と履歴引き継ぎを進めるか（ワークフロー編集はウェブ画面での作業が必要）。

## 推奨する進め方

課題2（定数化とテスト）→ 課題3（軽量化）→ 課題1は案1のみ先行し、統一はフォワード検証の蓄積後。いずれも着手前に改めて確認を取る。
